# Architecture Documentation

System architecture and design of the MCP Figma server.

## Overview

The MCP Figma server bridges Cursor AI and Figma through a WebSocket-based communication layer.

## System Components

### 1. MCP Server

**Location:** `figma-mcp-server/src/talk_to_figma_mcp/server.ts`

**Purpose:** Implements the Model Context Protocol interface

**Transport:** stdio (communicates with Cursor)

**Responsibilities:**
- Expose MCP tools and prompts
- Handle requests from Cursor
- Communicate with WebSocket server
- Manage channel connections

### 2. WebSocket Server

**Location:** `figma-mcp-server/src/socket.ts`

**Purpose:** Bridge between MCP server and Figma plugin

**Port:** 3055 (default)

**Responsibilities:**
- Manage WebSocket connections
- Route messages between MCP server and Figma plugin
- Handle channel management
- Provide connection status

### 3. Figma Plugin

**Location:** `figma-mcp-server/src/cursor_mcp_plugin/`

**Purpose:** Figma-side interface

**Components:**
- `code.js` - Plugin logic
- `ui.html` - Plugin UI
- `manifest.json` - Plugin configuration

**Responsibilities:**
- Connect to WebSocket server
- Execute Figma API calls
- Return results to WebSocket server
- Manage channel connections

## Communication Flow

```
Cursor → MCP Server (stdio) → WebSocket Server → Figma Plugin → Figma API
       ←                    ←                   ←              ←
```

### Request Flow

1. User makes request in Cursor
2. Cursor sends request to MCP server via stdio
3. MCP server forwards to WebSocket server
4. WebSocket server routes to appropriate channel
5. Figma plugin receives request
6. Plugin executes Figma API call
7. Results flow back through the chain

## Channel System

Each Figma plugin session creates a unique channel:
- Channel name is generated by plugin
- MCP server joins channel before operations
- WebSocket server routes messages by channel
- Multiple channels can exist simultaneously

## Data Flow

### Request Format

```typescript
{
  type: "request",
  channel: string,
  function: string,
  parameters: object
}
```

### Response Format

```typescript
{
  type: "response",
  channel: string,
  result: any,
  error?: string
}
```

## Error Handling

Errors propagate through the chain:
1. Figma API errors → Plugin
2. Plugin errors → WebSocket server
3. WebSocket errors → MCP server
4. MCP errors → Cursor

Each layer handles errors appropriately and provides context.

## Performance Considerations

### Batch Operations

- Functions support batch operations
- Process in chunks of 5 for large sets
- Progress updates during processing

### Chunking

- Large designs are automatically chunked
- Text scanning uses intelligent chunking
- Prevents timeouts and memory issues

### Caching

- Document info can be cached
- Component and style information cached
- Reduces redundant API calls

## Security

- WebSocket server runs on localhost only
- No external network access required
- Channel-based isolation
- No authentication needed (local only)

## Extension Points

### Adding New Functions

1. Add function to MCP server
2. Implement WebSocket handler
3. Add Figma plugin handler
4. Update documentation

### Custom Protocols

The architecture supports custom protocols:
- WebSocket protocol is extensible
- Channel system allows isolation
- Plugin can handle custom message types
